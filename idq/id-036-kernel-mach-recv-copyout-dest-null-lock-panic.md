## ROOT CAUSE FOUND (op-242, Arranger-verified first-hand 2026-07-02)
Not a double-drain UAF (that was the op-241 hypothesis) — a **flag collision**: libdispatch arms the public MACH_RECV source readiness-only with `.fflags = DISPATCH_MACH_RECV_MESSAGE = 0x2` (source_internal.h:66 / init.c:1250), and the kernel's `filt_machport` read `0x2` as `MACH_RCV_MSG = 0x2` (message.h:636) → did an in-kernel receive with no buffer → `MACH_RCV_TOO_LARGE` → `msg_receive_error` → `ipc_kmsg_copyout_dest` null-`io_lock` panic. Fix (ipc_pset.c:149, `filt_machport_direct_receive`): only take the direct-receive path when `ext[0]/ext[1]` carry a real buffer. CAVEAT (`code_reasoned_verdict_is_hypothesis`): the trace reproduces the panic SYMPTOM but the reproduced backtrace enters via `mach_msg_overwrite_trap` (syscall), not `filt_machport`; the filter→syscall-panic causal link is reasoned, not traced. Validator (op-246) closes that + the internal-direct-receive regression risk.

## THE FINDING (first-hand, op-241 @ explorer 4c96652)

A single-message `DISPATCH_SOURCE_TYPE_MACH_RECV` round-trip panics the kernel:
```
panic: mtx_lock() of spin mutex (null) @ ipc_kmsg.c:2844   (explorer-tree line; canonical io_lock(dest) at ipc_kmsg.c:2853)
ipc_kmsg_copyout_dest → msg_receive_error → mach_msg_receive
```
The dispatch source armed correctly (port allocated, source created/resumed, kevent fired — `filt_machport` delivered, op-098 path intact). The crash is in the kernel's message **error-return** copyout: `io_lock(dest)` on a port whose `io_lock_data` spin mutex is NULL. Reproducer: `rmx-explorer findings/nx-r64z/dtrace/mach-recv-premise/mach_recv_probe.c` (smallest falsifiable trigger).

## ROOT CAUSE IS NOT YET KNOWN — the op-241 report's proposed fix is REFUTED

op-241 proposed "ensure `insert_right` initializes `io_lock_data`." **Contradicted by the probe's own trace:** the `mach_msg(MACH_SEND_MSG)` on `recv_port` SUCCEEDED (kevent fired ⇒ message landed). The send path *also* `io_lock(dest)`s that same port; a NULL lock there would have panicked the SEND first. So the lock was non-NULL at send — the NULL-lock at receive-error copyout has a different cause. Candidates (Implementer must trace, not guess): stale/freed `dest` (use-after-free — the probe double-drains: dispatch source armed + handler's own `mach_msg(MACH_RCV_MSG)` on the same port), or a malformed kmsg header on the `msg_receive_error` path.

**Two questions the fix must answer FIRST (op-242 scope-1, kernel trace/KGDB before any edit — the op-240 discipline):**
1. Why does `mach_msg_receive` enter `msg_receive_error` at all (op-098's raw-round-trip receive succeeded)?
2. What is `dest` at the `io_lock` panic — real port w/ nulled lock (init/UAF), or a non-port pointer passing `IO_VALID`?

## op-244 RESIDUALS CARRIED (beyond R1 — anchored here so a green op-247 doesn't silently drop them; full detail: rmx-oracle/op-244-cort-lifetime-findings.md §3-§5)

**R2 — error-path hardening is a real kernel-robustness bug REGARDLESS of op-247's outcome.** op-244: a graceful `MACH_RCV_TOO_LARGE` must NEVER panic.
