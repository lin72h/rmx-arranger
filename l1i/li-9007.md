## WHAT IT MEANS

Finish the generic Mach receive contract for a queued message that is larger than the caller's
declared receive capacity:

1. return `MACH_RCV_TOO_LARGE`;
2. publish the required message size and, when requested, receiver identity;
3. keep the same message queued and its rights/resources intact;
4. let userspace allocate a sufficiently large buffer and retry the same message; and
5. preserve the ordinary non-`LARGE` and direct-kevent behavior.

This is **not an OOL-messaging implementation**. OOL memory and OOL-port descriptors already
exist. The receive buffer contains the header, inline data, descriptor records, and requested
trailer; the descriptor points to separately mapped OOL memory. A large OOL payload therefore does
not itself require an equivalently large receive buffer, although complex/OOL-bearing messages are
important lifetime and no-loss controls for this contract.

The long-arc payoff is public Mach/libdispatch compatibility for variable-size MIG requests,
port-set receivers, complex messages, future external consumers, and `dispatch_mig_server`-style
grow-and-retry code. It is not required by the named in-tree 1.0-preview stack.

## COORDINATOR SCOPE RULING — 2026-07-11

External/public syscall-`MACH_RCV_LARGE` callers are **excluded from the 1.0-preview contract**.
The build-aware op-313/op-316 census found no activated in-tree preview consumer of that syscall
family. This is an honest scope cut, not a claim that the API works and not removal of a working
NextBSD feature.

Consequences:

- preview op-281/op-282 are flushed without dispatch, runtime cell, or product edit;
- the current syscall defect remains cataloged here for deliberate post-preview repair;
- the exact-final-candidate Mach invariant replay remains in id-042, but it need not exercise an
  excluded external syscall-`LARGE` consumer;
- the separate **active libxpc trailer-admission boundary remains preview work under id-021**. It is
  not moved here merely because both concerns pass through receive-size admission.

## VERIFIED NEXTBSD / RMXOS BASELINE

### Nominal feature surface exists

The archived NextBSD source at `/Users/me/wip-mach/nx/NextBSD-NextBSD-CURRENT/` contains:

- `sys/sys/mach/message.h:637-638` — public `MACH_RCV_LARGE` and
  `MACH_RCV_LARGE_IDENTITY` flags;
- `sys/compat/mach/ipc/ipc_mqueue.c:621-637` — queue-first retain-and-size branch;
- `sys/compat/mach/ipc/mach_msg.c:540-577` — result helper intended to copy required size and
  receiver identity to userspace; and
- `lib/libdispatch/src/source.c:4191-4282` — `dispatch_mig_server` oversized-message handling.

NextBSD builds libdispatch with `DISPATCH_DEBUG=1` (`lib/libdispatch/Makefile:17`), which enables
that legacy `dispatch_mig_server` `MACH_RCV_LARGE` path.

### The synchronous syscall contract is incomplete

NextBSD's `sys/compat/mach/ipc/mach_msg.c:372` stores the full option in `ith_option` but passes only
`option & MACH_RCV_TIMEOUT` to `ipc_mqueue_receive`. The queue-first mqueue branch therefore cannot
see `MACH_RCV_LARGE` or the requested trailer size. The blocked receive path separately hands the
kmsg to the waiter before its size failure and lacks a complete retain/retry wake-state contract.

rmxOS inherited this shape. Retired Validator op-316 accepted the three-path source model and
op-282 brief incompleteness after the op-313 consult; its unconditional-bank/trailer conclusions
were narrow-adjudicated separately.

### No activated in-tree preview syscall consumer

The only apparent NextBSD in-tree `dispatch_mig_server` callers are Heimdal paths compiled under
`__APPLE__ && HAVE_GCD`; NextBSD's generated `kerberos5/include/config.h:376` leaves `HAVE_GCD`
undefined. Ordinary preview notifyd, ASL, launchd, libnotify, and libxpc do not set
`MACH_RCV_LARGE`. Libdispatch's direct Mach kevent mechanism is a separate receive mechanism and
does not establish the synchronous syscall contract.

External/public consumers remain possible. That unknown is why the defect is preserved here rather
than declared nonexistent.

## CONTRACT TO IMPLEMENT WHEN SCOPED IN

### Queue-first receive

- Preserve all size-relevant receive options through mqueue admission: at minimum `LARGE`,
  `LARGE_IDENTITY`, timeout, and trailer selection.
- On insufficient capacity with `LARGE`, do not dequeue or consume the kmsg.
- Publish the correct user-representation message size and requested identity.
- A retry with adequate capacity must receive the same message exactly once.

### Receive-first / blocked delivery

- Do not lose the kmsg merely because delivery reached a sleeping waiter before the final size
  check.
- Define the wake/result state for `MACH_RCV_TOO_LARGE` with `LARGE`; the result helper must accept
  and publish that state.
- Retain/requeue or use another proven mechanism that preserves ordering, identity, rights, OOL
  resources, and same-message retry.

### Trailer accounting

- Admission and copyout must use the same requested trailer size.
- Keep generic trailer-option correctness in the matrix, but do not use this L1i to defer id-021's
  already-live libxpc fixed-buffer premise.

### Non-`LARGE` and direct-kevent compatibility

- Preserve the existing non-`LARGE` error path and the op-249 uninitialized-kmsg correction.
- Preserve readiness-only and direct-kevent semantics; never use a kevent green as proof of the
  synchronous syscall path.

### Role / repository split

- **Explorer (`rmx-explorer`)** authors any new conformance/reproducer source and its expected
  behavioral contract.
- **Gatekeeper (`rmx-gatekeeper`)** owns a separate park/register/stage/run handoff, containment,
  guest cells, raw evidence, and runtime verdict. It must not author a duplicate local copy of an
  Explorer-owned corpus.
- **Implementer (`wip-gpt/wip-rmxos`)** alone changes and builds product source.
- **Validator** reads returned artifacts first-hand but writes no owning repository.

One op targets one named EXU/repository. Cross-repository authoring and registration are separate
ops; no op may tell an Explorer to write the Gatekeeper ledger or a Gatekeeper to edit product.

### P1 — contained evidence-first premise

After any required Explorer content-authoring op, a separate Gatekeeper op must establish
fail-closed known-bad controls before any kernel edit:

- queue-first and genuinely blocked receives;
- receive port and port-set identity;
- `LARGE` and `LARGE_IDENTITY` separately;
- minimum, audit, and context trailer sizes;
- inline-variable, complex/OOL-memory, OOL-ports, and transferred-right messages;
- exact fit, one-byte-short declared capacity, and next valid aligned oversize;
- proof that the same message remains available and no right/VM resource is leaked; and
- direct-kevent plus ordinary non-`LARGE` regression controls.

Runtime start consumes a guest cell. Host static inspection may prepare the premise, but target
execution, `dlopen`, or target-linked probes require containment.

### P2 — high-blast-radius product correction

Only after P1 acceptance and Coordinator release, a new Implementer op owns the kernel change.
Bind the option plumbing, result-copyout/identity sites, blocked wake state, and retention mechanism
explicitly. One op targets only the product repository; no harness or control-repo write is mixed
into it.

### P3 — independent correctness and runtime acceptance

- L/XL source/lifetime review goes to a Validator.
- Gatekeeper reruns the exact known-bad/known-good matrix on the exact built and staged artifact.
- Acceptance proves same-message retry, ordering, identity, rights/OOL-resource conservation, and
  no regression across the named ordinary services.
- Product retirement requires origin reachability.

### P4 — consumer enablement

Only after the substrate is accepted may a concrete consumer enable or depend on the syscall path:
`dispatch_mig_server`, variable-size MIG services, or another public Mach client. Each consumer
still needs its own compatibility and bounded-buffer evidence.

## TRULY-GREEN BAR

1. Exact public/source/product/image identities are pinned.
2. Queue-first and blocked paths both return `MACH_RCV_TOO_LARGE` with the correct size and optional
   identity while preserving the same message.
3. Adequate retry receives that message once; a second retry does not duplicate it.
4. Inline, complex/OOL-memory, OOL-ports, transferred-right, and trailer cases conserve rights,
   mappings, queue depth, and ordering.
5. Non-`LARGE`, timeout, trailer, port-set, readiness-only, and direct-kevent controls do not
   regress.
6. Known-bad current behavior is rejected by the same detector that accepts the result.
7. Independent validation and contained runtime acceptance agree; the product commit is
   origin-reachable.
