## BACKLOG

### Item 1 — Trailer-identity fiction: unconditional kernel tokens + stubbed receive-side trailer formatting (op-223 N3; trailer-identity premise Arranger-verified first-hand)
- **What:** all tasks carry KERNEL trailer/security tokens unconditionally (`sys/compat/mach/kern/task.c:215-216`), and receive-side trailer formatting is `#ifdef notyet` (`sys/compat/mach/mach_msg.c:599-603`). So the msg-trailer sender-identity / audit-token surface is a **fiction** — everything reads as "kernel."
- **Why it matters:** any consumer that trusts a message trailer's sender identity or audit token gets a constant kernel token, not the real peer. Works today only because nothing consumes it (formatting stubbed). Latent correctness/fidelity gap vs macOS — bites the moment a trailer-consuming feature lands (xpc peer identity, audit tokens, entitlement checks).
- **Disposition (Coordinator 2026-07-02 — deferred, do NOT pull forward):** op-223 N3 argued for stamping honest {uid,gid}-grade tokens *now*, before LEG B (launchd/xpc) hardens on top. Coordinator ruled it does **not** block the 1.0-preview (works today — trailer formatting stubbed, nothing consumes it) → delayed. Catalog; promote to an Implementer op only when a trailer-consuming feature is actually scoped in. This is N3's durable home.
- **Long-term arc (op-223 L1, post-preview / milestone-2 conformance-completeness):** the *receive-side* half — un-`notyet` `ipc_kmsg_add_trailer` (`mach_msg.c:599-603`) to format real seqno/context/audit elements per the receiver's rcv options — pairs with the N3 token-stamping (the *send-side* identity). Together they're the two halves of making the trailer surface honest; both deferred, sequenced when a trailer-consuming feature lands. Conformance-completeness arc, not a preview gate.

### Item 2 — Conditional-lock idiom, correctness depends on caller-context (`ipc_object.c:119-145`)
- **What:** a lock idiom whose correctness depends on the caller reasoning about context, not on the idiom itself. Cheap to misuse in a future edit that doesn't know the contract.
- **Disposition:** low-cost hardening — add a `_Static_assert`/`KASSERT`/contract-comment or refactor to a self-documenting form when this file is next touched. Not urgent; a latent-defect seed for future edits.

### Item 3 — Mixed trap return conventions + trap-surface burn-down (`mach_traps.c`, e.g. `:238` vs `:326`; burn-down = op-223 L4)
- **What:** sibling traps use inconsistent return conventions (`retval[0]` vs errno). Beyond the local inconsistency, op-223 L4 frames a **post-preview burn-down arc**: implement or formally `UNSUPPORTED`-document the still-hollow trap families — the **semaphore traps** (`mach_traps.c:142-158`, the native-primitive build tracked in **li-9003 Item 3**) and the **`port_construct`/`guard` family** (`mach_traps.c:314-336`) — normalizing the retval[0]-vs-errno convention as each is touched.
- **Disposition:** normalize when the file is touched; pairs naturally with a trap return-edge exerciser (Item 5). **Schedule the burn-down per actual LEG B service need, not speculatively** — a family stays `UNSUPPORTED`-documented until a real consumer forces implementing it. Consistency/readability hardening + honest unsupported-surface. (Semaphore *semantics* live in li-9003 Item 3; this item owns the trap-convention + honest-stub discipline.)

### Item 4 — Dead XNU munging block (`mach_traps.h:316-391`)
- **What:** a dead XNU-derived argument-munging block that already **consumed one op** (the enable+revert no-op pair at tip — op-171-adjacent LP64 munging churn).
- **Disposition:** delete candidate — a **recorded informed drop** (same pattern as li-9003 Item 1's dead blocking arm): git history + the XNU reference preserve the design if ever needed. Retire deliberately rather than carry-forever or delete-blind.

### Item 5 — Test-coverage gaps visible from source (IPC/dispatch)
- **What (enumerated):** no exerciser for (a) trap return-convention edges (ties to Item 3); (b) trailer-option size paths — `MACH_RCV_TRAILER_MASK` returns option-*computed* sizes over statically-stamped content (`mach_msg.c:390`, `:521`); (c) the ENOSYS fallback chain (THRWORKQ-absent → pthread pool); (d) `close(2)`-on-port-fd semantics (the port-as-fd destructor path, cross-ref li-9002 Item 1's always-on invariant). The kqueue filter's receive path is exercised **only** via dispatch's own usage — no direct filter test.
- **Disposition:** each is a Gatekeeper/Explorer conformance-probe candidate; promote alongside the related fix (e.g. (a) with Item 3, (d) with the li-9002 port-fd invariant). Coverage-debt, not a gate.

### Item 6 — Private kqueue-internals walk on the message activation path (`ipc_pset.c:488-516`; op-223 N5; Arranger-verified first-hand 2026-07-02)
- **What:** `ipc_pset_signal` hand-rolls the knote walk — `SLIST_FOREACH` over `kl_list` with manual `KQ_LOCK`/`kn_status |= KN_ACTIVE`/`knote_enqueue` (private kqueue internals). Verified first-hand: the same subsystem *already* uses the public `KNOTE(&pset->ips_note, EV_EOF, KNF_LISTLOCKED)` idiom three times in `ipc_right.c` (`:517`, `:627`, `:957`), so the idiomatic replacement is precedented in-tree, not novel.
- **Why it matters:** private-API coupling on the message activation (send→receive-set-wakeup) path. Every FreeBSD base bump that touches kqueue internals (`kn_status` bits, `knote_enqueue` signature, list layout) can silently break this walk, while the `KNOTE()` callers stay churn-proof. One activation idiom across the subsystem is both safer and self-documenting.
- **Disposition:** small mechanical refactor — replace the private walk with `KNOTE()`+hint, matching `ipc_right.c`. Cross-refs **li-9002** (base-rebase): this is exactly the kind of base-coupled surface that register re-verifies on a bump. Promote when the file is next touched or when a base sync flags kqueue-internal drift.

### Item 7 — SEND_POSSIBLE: dispatch arms a notification the kernel doesn't deliver (op-223 #4/N4; Arranger-verified first-hand 2026-07-02; **delayed here from li-1013 by Coordinator ruling 2026-07-02**)
- **What:** libdispatch arms `MACH_NOTIFY_SEND_POSSIBLE` (`lib/libdispatch/src/source.c:2875-2950`, `_dispatch_mach_notify_update`); the kernel's `mach_port_request_notification` arms only PORT_DESTROYED / NO_SENDERS / DEAD_NAME, so SEND_POSSIBLE falls to `default → KERN_INVALID_VALUE` (`sys/compat/mach/ipc/mach_port.c:1200-1270`). Verified first-hand: the return threads to `dispatch_assume_zero` (`source.c:2625-2637`) — a soft-assert log, **not** a functional degrade path. A send-possible-armed client gets a logged non-zero + no notification, not a graceful no-op.
- **Why it matters:** works today only if nothing live arms it. Latent send-right-state-machine gap: the moment a dispatch client (or a service on top) requests send-possible edges, it silently mis-behaves.
- **Disposition (Coordinator 2026-07-02 — NOT a preview gate, delayed):** two branches (op-223 N4) — either implement the kernel arm (`mach_port.c:1200` switch) OR formally document the degradation + verify the dispatch failure path is benign. **Trace-first before either:** does any live client arm SEND_POSSIBLE? If a trace ever finds a live *preview* consumer → **escalate back to li-1013** (it would then sit on the ship path). Until then it stays deferred here. verify-premise-before-mechanism: no fix op before a live consumer is confirmed.

### Item 8 — op-215 de-spam gate mutes an un-root-caused lookup-failure emitter (op-223 quality observation; Arranger-verified first-hand 2026-07-02; **delayed here from li-1013 by Coordinator ruling 2026-07-02**)
- **What:** op-215 added a **default-off sysctl** de-spam gate over a port-lookup-failure log path (`sys/compat/mach/ipc/ipc_kmsg.c` ~:1325). It quiets the *symptom* (log firehose) but the lookup failures still occur — now invisibly. A mute, not a fix; the signal for how-often/why is off by default.
- **Why it matters:** we don't actually know whether the lookup misses are benign (stale name / expected race) or a real defect, and the diagnostic that would tell us is dark. Correctness-hygiene debt on the IPC hot path.
- **Disposition (Coordinator 2026-07-02 — NOT a preview gate, delayed):** root-cause the emitter with the gate turned **on** in a controlled soak (pairs naturally with a li-1007 integration-soak lane, gate-on), then either (a) confirm-benign + document + keep default-off, or (b) fix the emitter. Not an independent op until scoped in; mute stays default-off meanwhile.

### Item 9 — Task refcount machinery: finish it or formally retire it (op-223 L3; **Oracle-cited, to be re-verified at promotion**)
- **What:** `task.c:268-276` carries a `ref_count` field + machinery, but the dominant accessor (`thread.h:633-639`) takes **no** references — so the refcount exists as a half-wired fiction rather than a working lifetime discipline. op-224 (N1) fixes the one *live* under-count on the insert_right path, but that's a tourniquet, not a resolution of the machinery.
- **Why it matters:** a partially-wired refcount is a latent-correctness footgun — future edits may trust it (take/drop refs) while the dominant path ignores it, inviting exactly the insert_right-class imbalance op-224 patches. Either it's a real discipline or it's dead weight; leaving it half-alive is the hazard.
- **Disposition (design-call FIRST, then mechanical):** decide the lifetime model — **(a) finish it** (real references everywhere + assert-on-underflow), or **(b) remove `ref_count` and document task lifetime as process-bound**. This is a Coordinator design decision, not a mechanical edit; op-224 holds the line until it's made. Cross-ref **op-224** (the N1 tourniquet on the same machinery). Re-verify the cited accessor at promotion.
