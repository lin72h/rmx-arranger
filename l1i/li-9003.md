# li-9003 — potential-features catalog (dormant/latent capabilities we COULD build or revive — decide deliberately, never by accident)

li-9003 | tier: L1i | milestone 9 (infrastructure / long-arc) constituent | status: **OPENED — LIVING CATALOG** (accretes a candidate each time a review finds latent capability worth a deliberate keep-or-drop call) | owner: Coordinator owns scope-in / promotion; Arranger catalogs + verifies | authored 2026-07-02 (Arranger seat, model Opus 4)

## WHAT IT MEANS

A catalog of **potential features** — capabilities that exist latently in the tree (imported-but-dormant machinery) or are natural extensions we could pursue, but that are **not** committed work today. Distinct from li-1008 (*known gaps* the preview steps around) and li-9002 (*rebase re-verify* of code we depend on): this is the **opportunity** register. Its job is to make sure a dormant capability is kept, revived, or retired **by an informed decision**, not by accident (e.g. deleting dead code without realizing it was a feature, or carrying it forever without knowing why).

Each item records: what the capability is, its provenance (so we know what we'd be reviving), why it's dormant, the realistic payoff/cost, and a **default disposition** pending a Coordinator scope-in. Nothing here gates the preview.

## CATALOG

### Item 1 — In-kernel Mach RPC via migrating threads (the dormant `thread_pool` / thread-activation machinery) — from op-223 finding #10, Arranger-verified first-hand

- **The capability:** classic-Mach **migrating threads / in-kernel RPC** — a client's call "migrates" into a kernel server by grabbing an activation from a pool of kernel thread *activations* parked on a port/port-set. Implemented by `sys/compat/mach/kern/thread_pool.c` (`thread_pool_get_act`, activations linked via `ith_pool_next`, blocking via `thread_block()`), built on the `thread_shuttle` + `thread_act` split.
- **Provenance (verified from the file header):** OSF Mach (1991-1998) + University of Utah CSL (1993, **author Bryan Ford** — the migrating-threads research), routed through **MkLinux**. **Imported wholesale by NextBSD** from that OSF/Utah drop, header preserved verbatim — NOT NextBSD-authored, and NOT copied from modern XNU. Apple's XNU descends from the same CMU/OSF ancestor but **removed this model** years ago (collapsed `thread_shuttle`/`thread_act` into a single `thread_t`). So it is *pre-XNU legacy Mach*, older than what Apple ships.
- **Why dormant:** our port delivers messages to **userland** receivers over the fd/kqueue path and runs on **FreeBSD threads** (`thread_block()` = `msleep` on `curthread`), so the in-kernel activation model is never used — all 5 call sites pass `block=0` (ipc_mqueue.c:450,453; ipc_port.c:602; ipc_pset.c:411,424), leaving the blocking self-park arm (+`printf`s at :119/:146) dead. The pool-as-a-list *non-blocking drain* path IS still referenced (wakes waiting receivers); only the blocking half is inert.
- **Realistic payoff / cost:** payoff only materializes IF rmxOS ever wants **high-performance in-kernel Mach servers** (RPC serviced in-kernel rather than by userland daemons). Cost is large and speculative: it depends on a threading model (act/shuttle split) our FreeBSD-hosted compat layer doesn't run, and it's a design Apple themselves abandoned — reviving it means re-porting a model, not flipping a flag. Low likelihood of ever being worth it given our userland-daemon architecture.
- **Default disposition (pending Coordinator):** **retire the dead blocking arm** (this is op-223 N7 cleanup — delete the `block != 0` path + the committed `printf`s; keep the live non-blocking drain). Cataloging it here means the deletion is a *recorded, informed* drop, and git history + the OSF/Utah/XNU references preserve the design so a future in-kernel-RPC decision can revive it from source if ever scoped in. Revisit ONLY if a concrete in-kernel Mach-server need appears.

### Item 2 — The real three-layer libdispatch workqueue engine (Apple-style THRWORKQ path, dormant on the shipping kernel config) — from op-223 finding #3, Arranger-verified first-hand

- **The capability:** the full Apple-architecture concurrency engine — dispatch → libthr userland runtime (`lib/libthr/thread/thr_workq.c`: lanes/buckets, reaper, `twq_kernel_init`/`TWQ_OP_INIT`) → in-kernel workqueue (`sys/kern/kern_thrworkq.c`, 1129 lines; `sys_twq_kernreturn` dispatching INIT/THREAD_ENTER/RETURN/TRANSFER/REQTHREADS/SHOULD_NARROW/SETUP_DISPATCH). Fine-grained priority lanes, kernel-managed thread requests — the same design macOS ships.
- **Provenance (verified at source):** the whole stack is present and wired. dispatch is built to use it (`Makefile` `HAVE__PTHREAD_WORKQUEUE_INIT=1`, `NXPLATFORM_DISPATCH_TWQ_WORKQUEUE=1`); libthr's `_pthread_workqueue_supported()` advertises `DISPATCHFUNC|FINEPRIO|MAINTENANCE` (`thr_workq.c:196-201`, a **constant**, no kernel probe); the kernel side is real code — but the entire `sys_twq_kernreturn` body is `#ifdef THRWORKQ ... #else return (ENOSYS)` (`kern_thrworkq.c:1058-1079`).
- **Why dormant:** `THRWORKQ` is a config option (`sys/conf/options:257`) present **only in MACHDEBUGDEBUG** (`sys/amd64/conf/MACHDEBUGDEBUG:7`); **MACHDEBUG** (GENERIC + COMPAT_MACH) does NOT carry it. On a no-THRWORKQ kernel the kernel returns ENOSYS, but libthr still advertises FINEPRIO unconditionally, so dispatch *tries* the real path, it fails, and dispatch **silently** falls back to the force-compiled-in userland pthread pool (`queue.c:27-33` `DISPATCH_ENABLE_THREAD_POOL`/`USE_PTHREAD_POOL`; cascade `:748-826` → sentinel `dgq_kworkqueue=(void*)(~0ul)` `:815`; `_dispatch_root_queues_init:873` → pool). Verified first-hand 2026-07-02: the fallback is silent (`assume_zero` at `:782` only logs), FreeBSD skips QoS attrs in the pool (`#ifndef __FreeBSD__ :841`), pool mediator is a POSIX sem (`:859-862`). Dispatch is **correct on both engines** — this is graceful degradation, not a bug.
- **Realistic payoff / cost:** payoff = the genuine Apple concurrency model (kernel-managed fine-priority thread requests) instead of a userland pool that ignores QoS on FreeBSD. Cost = promote THRWORKQ into the shipping kernel config + prove the kernel `sys_twq_kernreturn` path under load (it has never been the default-kernel engine). Real work, but the code already exists — this is *activate + validate*, not *port from scratch* (contrast Item 1).
- **Default disposition (pending Coordinator — this IS escalation E1; refined by op-225):** two-part. **(a) Decision:** is the real workqueue in 1.0-preview scope, or is the pthread-pool fallback an accepted preview engine? Coordinator-held acceptance-bar call (= op-225 C2). **(b) Evidence hygiene, do regardless:** every dispatch/concurrency green must record *which kernel → which engine* produced it (a green on the pool does NOT prove the real workqueue works), and the silent fallback should be made **loud** — an init-time log of which engine dispatch actually bound to (op-223 N2 banner) — so greens are attributable, not assumed. **Ship conf RESOLVED (op-182, verified op-225):** the preview image ships **MACHDEBUGDEBUG**, which *has* THRWORKQ — so the real engine IS reachable on the ship image; my earlier "if it ships MACHDEBUG" hedge is settled. **Residual (real) gap:** THRWORKQ-in-conf ≠ this-run-rode-twq — libthr advertises FINEPRIO with no kernel probe (thr_workq.c:196-201) and the fallback is silent, so an engine claim still needs *per-run* evidence (N2 banner or dtrace of twq syscalls). AND historical soaks ran the harness default **MACHDEBUG** (stage-guest.sh:74), i.e. the pool — so those greens must be re-hosted on the MACHDEBUGDEBUG ship image (li-1012 P2).

### Item 3 — Real Mach semaphore primitives (the wait/signal trap family, currently a wired-but-hollow shell) — from op-223 finding #4, Arranger-verified first-hand; user flagged as a foundational feature 2026-07-02

- **The capability:** native **Mach semaphores** — `semaphore_create` + the `semaphore_wait`/`_signal`/`_wait_signal`/`_signal_thread`/`_signal_all`/`_timedwait`/`_timedwait_signal` trap family, a core Mach IPC synchronization primitive (kernel-backed, port-named, supports cross-task semaphore ports and LIFO wakeup policy — things POSIX semaphores can't express). Many Darwin subsystems assume it; libdispatch's pool mediator explicitly wants `SYNC_POLICY_LIFO` (`queue.c:854`, the `#if USE_MACH_SEM` arm).
- **Provenance (verified at source):** NextBSD wired the trap **table entries** (`mach_module.c:226-232`, `SYSCALL_INIT_HELPER` for all seven) and shipped a `semaphore_create` **MIG server routine** (`task_server.c:3583`) — but the operations that make it useful are **stubs**: `sys_semaphore_wait/_signal/_wait_signal/_signal_thread/_signal_all_trap` are the `UNSUPPORTED` macro (`mach_traps.c:142-158`); `sys_semaphore_timedwait/_timedwait_signal_trap` are `return (ENOSYS)` (`mach_misc.c:90-107`). So it's a create-shell over hollow wait/signal traps — **NextBSD never implemented the semantics**, confirming the user's read.
- **Why dormant:** because the traps are hollow, libdispatch is configured `USE_POSIX_SEM=1` / `USE_MACH_SEM` **undefined** (`config/config.h:175,:178`) and emulates blocking with the POSIX-sem path. There is no live consumer of the Mach-sem traps today.
- **Realistic payoff / cost:** payoff = a genuine kernel Mach synchronization primitive (LIFO policy, cross-task semaphore ports, no userland poll) — foundational for Mach-native code and lets libdispatch flip to `USE_MACH_SEM`. Cost = implement wait/signal/timedwait semantics in the compat layer over FreeBSD sync primitives (sleepq/cv), backed by the ipc-object/port model; **bounded, not from-scratch** — the trap table + create shell already exist, so it's filling bodies + a backing object, not new syscall plumbing.
- **Default disposition (pending Coordinator):** **near-term = accept the POSIX-sem interim** (works today; the poll→non-polling `sem_clockwait` polish is tracked in id-005, a separate POSIX-side axis — do NOT conflate). **Future = build the native Mach semaphore primitives** (this item) as foundational investigation; revisit when a Mach-native consumer needs true Mach-semaphore semantics (LIFO wakeup / cross-task ports) that POSIX cannot provide. Cataloged here so the build is an informed, scoped decision — not an accidental "the traps exist, just fill them in" drift.

### Item 4 — QoS un-collapse: real quality-of-service lane propagation onto the twq engine (op-223 L2; **Oracle-cited, to be re-verified at promotion**)

- **The capability:** honest **QoS-class propagation** end to end — dispatch's priority TSD arm (`shims/tsd.h:62-92`, `queue.c:4073`) carrying a request's QoS class into the workqueue, mapped onto twq's priority lanes (the `thr_workq.c` bucket machinery already exists). macOS schedules dispatch work by QoS; we currently do not.
- **Why dormant:** the FreeBSD compat layer **pins LEGACY→DEFAULT** (`freebsd_compat.h:90-91`), collapsing every QoS class to one lane, and the pool engine skips QoS attrs entirely on FreeBSD (`queue.c:841` `#ifndef __FreeBSD__`, cross-ref Item 2). So QoS is *expressed* by clients but *flattened* before it reaches any scheduler.
- **Realistic payoff / cost:** payoff = genuine QoS-differentiated scheduling (the macOS behavior). Cost = **sizable and scheduler-adjacent** — it touches priority behavior, so it belongs with real-hardware / performance work, and it is **gated behind Item 2**: QoS lanes are meaningless until the real twq engine (not the QoS-blind pool) is the live engine. Un-collapse without the engine buys nothing.
- **Default disposition (pending Coordinator):** catalog; **sequence after Item 2** (real workqueue engine live first), then trace the TSD arm + unpin LEGACY→DEFAULT + map classes onto twq buckets. Perf/real-HW milestone territory, not speculative pre-work. Re-verify the cited locations first-hand at promotion.
