# li-9002 — FreeBSD base-rebase checklist (the living "what to re-verify when we sync/bump the FreeBSD base")

li-9002 | tier: L1i | milestone 9 (infrastructure / long-arc) constituent | status: **OPENED — LIVING CHECKLIST** (accretes an item each time we find code coupled to base internals; run in full on every base sync/bump) | owner: Coordinator owns scope-in of any fix op; Arranger maintains the checklist | authored 2026-07-02 (Arranger seat, model Opus 4)

## WHAT IT MEANS

rmxOS is a Mach userland + `COMPAT_MACH` kernel module carried on a **fork of stock FreeBSD 15/stable**. Some of our code is coupled — knowingly — to **base-kernel internals** that FreeBSD keeps private (`static`, or layout/ABI that can shift between releases). That coupling **works against today's base** but can break when we **rebase / sync / bump the FreeBSD base**, and the dangerous cases break **silently** (still compiles, wrong behavior at runtime) rather than loudly.

This li is the **living checklist** of every such coupling point: what it is, why it's fragile across a base bump, and the concrete re-verify / guard step to run at rebase time. It is NOT a feature and NOT a preview gate — it is a maintenance instrument that protects the port across base updates. New items are appended as reviews (op-223 and successors) surface them.

## HOW TO USE

- **Trigger:** any FreeBSD base rebase, stable/15 sync, or release bump.
- **Action:** walk every item below; run its re-verify step; fix or re-sync before declaring the rebase clean.
- **Preferred end state per item:** convert each silent-drift hazard into a **loud, compile-time tripwire** (e.g. `_Static_assert`/`CTASSERT` on the base fact the code depends on) so the *next* rebase fails the build instead of shipping a latent corruption.

## CHECKLIST

### Item 1 — fd-internals shadow copies in the Mach IPC layer (from op-223 LEG A review, finding L5; Arranger-verified first-hand)

- **What:** `sys/compat/mach/ipc/ipc_entry.c` carries **private copies** of FreeBSD file-descriptor internals — re-implemented `fdunused` / `kern_fdalloc` / `kern_fddealloc` / `kern_fdfree` / `kern_finstall` (declared :153-159, bodies ~:858-1000) — plus direct pokes at `struct filedesc` fields (`fd_ofiles`, `fd_map`, `fd_freefile`, `fd_nfiles`, `fd_refcnt` via `NDSLOT`/`NDBIT`/`FILEDESC_XLOCK`), and hardcoded constants (`DTYPE_MACH_IPC 17`, `KF_TYPE_PORT/PORTSET 17/18`, `FNOFDALLOC 0x80000000`, the `MODERN = __FreeBSD_version >= 1100000` gate) at :162-178. These exist because base keeps `fdalloc`/`finstall`/`fdfree`/`fdunused` `static` in `kern_descrip.c` (not exported), so the port-as-fd design copied them out.
- **Why fragile across a base bump:** the copies are a frozen snapshot. If base changes `struct filedesc` layout, fdtable-growth logic, the fd locking protocol, or renumbers a dtype, the copies **still compile** (same field names) but operate on stale assumptions → memory corruption / lock-protocol violation at runtime, with **no build error**. Verified 2026-07-02: **no tripwire exists today** (no `_Static_assert`/`CTASSERT`); `MODERN` is a coarse version macro, not a layout guard; `DTYPE_MACH_IPC` is already defined in base `sys/sys/file.h:77`, so the local `#ifndef` fallback is redundant and gives false comfort (base wins on any change; the fallback never fires).
- **Re-verify at rebase:** diff base `kern_descrip.c`'s `fdalloc`/`fdfree`/`finstall`/`fdunused` and the `struct filedesc` definition against our copies; re-sync if changed.
- **Preferred guard (near-term, cheap):** add `_Static_assert`s on `sizeof(struct filedesc)` + key field offsets and on `DTYPE_MACH_IPC == 17` next to the shadow code, so a base layout/constant change fails the build loudly. Delete the redundant local constant fallbacks so a mismatch is a redefinition error, not a silent divergence.
- **Durable fix (long-arc, Coordinator-scoped — touches the base fork):** add a small **exported extension point** in our fork's `kern_descrip.c` (export `finstall`/`fdalloc`, or a purpose-built `kern_mach_fdinstall`) so the Mach layer calls the genuine routines instead of carrying copies — eliminates this drift class entirely. Brushes the "don't touch FB15 build infra" rule, but it's *our fork* and a scoped source-of-truth fix, so it needs a Coordinator call vs. keeping the tripwire band-aid.
- **Related but NOT a rebase item (always-on design property, listed for context):** because a Mach port is a real fd, `close(2)`/`closefrom(2)`/exec/exit can destroy it — a destructor path real Mach never had. Works today only via `mach_fileops.fo_close = mach_port_close`. Invariant to enforce independent of base bumps: *every port-backed right-type must implement `fo_close`; never assume a port dies only through the Mach API.* Back it with a close(2)/closefrom(2)-on-port-fd teardown conformance probe. (Tracked here as context; it belongs to the IPC-layer invariants, not the rebase trigger.)
