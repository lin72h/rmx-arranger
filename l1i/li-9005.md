## WHAT IT MEANS

Swift's public `TaskPriority` accepts every `UInt8`, but the Swift 6.4 Dispatch global executor
currently indexes a 34-entry queue cache directly and fatals for raw values above 33. Swift
[PR #90000](https://github.com/swiftlang/swift/pull/90000) closes that domain mismatch by
canonicalizing every raw value into one of five Dispatch QoS classes before selecting a queue.

For rmxOS this is **correctness and integration first, performance second**:

- **8/10 Swift–rmxOS integration prerequisite:** arbitrary legal `TaskPriority` values must not
  abort, and the canonical class must reach the intended rmxOS workqueue admission lane.
- **3/10 standalone performance optimization today:** rmxOS already differentiates explicit TWQ
  admission lanes, but current-thread QoS, priority overrides, inheritance, and actual CPU
  scheduling priority are not yet macOS-equivalent.

This instruction owns the complete, deliberately staged arc:

1. canonicalize arbitrary Swift priorities and close the native libdispatch ABI needed by delayed
   jobs;
2. prove five-class behavior on both rmxOS dispatch engines without hiding which engine ran;
3. implement honest per-thread QoS/override/inheritance semantics and decide how they affect ULE;
4. only then evaluate Swift task stealing/cooperative scheduling.

Nothing here gates li-1000. Opening the design/experiment track does not authorize importing a
draft upstream patch or editing either product tree.

### Upstream state and exact mapping

As checked from GitHub on 2026-07-11, PR #90000 remains **open, draft, and unmerged**, at head
`a6f32e5e29a63fa64770f4ae7abbc315a1482652`. It replaces raw-value indexing with this ceiling map:

| Swift raw priority | Dispatch QoS class |
|---:|---|
| 0…9 | background |
| 10…17 | utility |
| 18…21 | default |
| 22…25 | user initiated |
| 26…255 | user interactive |

The five-entry cache and mapping are visible in the
[pinned patched executor](https://github.com/swiftlang/swift/blob/a6f32e5e29a63fa64770f4ae7abbc315a1482652/stdlib/public/Concurrency/DispatchGlobalExecutor.cpp#L64-L104).
The upstream discussion records both a platform-specific crash boundary and an unresolved concern
that raw maintenance priority `0x05` is promoted into background. Treat those as test/policy inputs,
not settled rmxOS doctrine.

### rmxOS path that already exists

First-hand source was read in local product `alpha@7291ad2` (an unpublished local source premise,
not retirement evidence):

```text
Swift TaskPriority
  → PR #90000 five-class canonicalization
  → rmxOS libdispatch queue QoS / encoded pthread_priority_t
  → libthr TWQ lane
  → kernel TWQ admission and concurrency control
  → ordinary FreeBSD ULE worker thread
```

- `lib/libdispatch/src/queue.c:748-770` initializes the fine-priority workqueue interface, and
  `:3378-3380` passes a root queue's encoded `dq_priority` to
  `_pthread_workqueue_addthreads()`.
- `lib/libthr/thread/thr_workq.c:808-824` selects pending lanes from user-interactive downward.
- `sys/kern/kern_thrworkq.c:337-367` subtracts higher-class occupancy from lower-class admission.
- `lib/libthr/thread/thr_workq.c:130-150` provides `LIBPTHREAD_TWQ_TRACE`, including bucket/lane/
  priority evidence suitable for the laboratory gate.

Therefore canonicalization is not cosmetic on a live TWQ engine: it prevents Swift from treating
arbitrary raw priorities as independent queues/fatal values and gives rmxOS five meaningful
admission classes.

## CORRECTED QOS PREMISE — ADMISSION IS NOT CPU PRIORITY

The historical li-9003 Item 4 claim that FreeBSD collapses *every* QoS class is no longer true of
the current tree. `freebsd_compat.h:90-93` aliases only `QOS_CLASS_LEGACY` to default and redirects
one priority TSD key; explicit queue `dq_priority` values still reach the bucketed TWQ path above.

The remaining gaps are real and must stay visible:

- `qos_class_self()` and `qos_class_main()` return default unconditionally
  (`thr_workq.c:1355-1367`).
- `pthread_set_qos_class_self_np()` validates but records no state (`:1369-1375`).
- direct QoS/workqueue priority override entry points are successful no-ops (`:1409-1459`).
- Swift's non-Apple path does not inherit the current external thread's QoS and creates five
  private width-limited queues rather than using Apple's cooperative global-root queues.
- rmxOS's present effect is lane selection and admission pressure; it does not yet prove a
  corresponding ULE CPU-priority change, donation, escalation, or inversion avoidance.
- the pthread-pool fallback skips the TWQ lane machinery and must be measured and reported as a
  separate engine, never presented as equivalent evidence.

Accordingly the P1 result may be called **priority canonicalization green**. It must not be called
macOS QoS parity or scheduling-performance green.

## ABI CLOSURE DISCOVERED WITH THE PRIORITY TRACK

The immediate-task path is close to ABI-ready, but the delayed/leeway path is not:

- Swift `DispatchGlobalExecutor.cpp:370-386` creates a timer source and calls
  `dispatch_activate(source)`.
- Native rmxOS classic libdispatch implements `dispatch_resume()` in
  `lib/libdispatch/src/object.c:241-265`, but exports no `dispatch_activate` implementation or
  declaration.
- `dispatch_async_swift_job` is also absent, but this is **not a correctness blocker**: Swift
  dynamically probes it and falls back to `dispatch_async_f` (`DispatchGlobalExecutor.cpp:84-126`).

`dispatch_activate` is therefore a load-bearing P1 ABI gate. The owning Implementer must close it
in native rmxOS libdispatch with verified source-compatible semantics before delayed/leeway Swift
jobs can be accepted. Do not silently substitute `dispatch_resume` without verifying the modern
activation contract.

For a laboratory-only comparison, a matching swift-corelibs-libdispatch build may be useful. The
product path must load **one** libdispatch implementation: either close the Swift-facing ABI in
native rmxOS libdispatch or perform an explicitly scoped modern rebase that preserves rmxOS Mach/
TWQ integration. Two simultaneously loaded dispatch implementations are forbidden.

1. Capture the unpatched raw-34 abort as a negative control.
2. After the experimental change, run every raw value `0…255` and assert its five-class mapping.
3. Trace boundary values `0, 9, 10, 17, 18, 21, 22, 25, 26, 33, 34, 255`.
4. Exercise immediate tasks and delayed/leeway timer tasks; the latter is fail-closed on the

6. Observe completion with semaphores or an equivalent non-escalating primitive. Do not use
   `await task.value` as the primary observation because Swift documents that awaiting can elevate
   the awaited task.
7. On TWQ, retain `LIBPTHREAD_TWQ_TRACE` evidence proving raw-boundary → canonical class → encoded
   priority → lane/bucket. On the pool, report the actual behavior and any accepted limitation.

### P2 — real rmxOS thread QoS and override semantics

  prove `qos_class_self()` observes the effective class.
- Decide and verify whether classes affect only TWQ admission or also ULE CPU scheduling priority.
- Design external-thread inheritance for the Swift FreeBSD path rather than pretending rmxOS is

### P3 — task stealing / cooperative scheduling

Only after P2 is real, evaluate Swift
[PR #86082](https://github.com/swiftlang/swift/pull/86082) (task stealers) and any cooperative
workqueue work. As checked 2026-07-11, #86082 is open and unmerged.

Do **not** define `__APPLE__` to select Swift's Apple branch. Native rmxOS libdispatch rejects the
cooperative global-queue flag (`dispatch_get_global_queue`, `queue.c:567-572`), and the declared TWQ
cooperative flag has no active mechanism. Cooperative behavior requires its own design, product
implementation, and evidence.

## TRULY-GREEN BARS

### P1 — priority canonicalization green

1. The exact Swift patch/head and rmxOS product/image identities are pinned.
2. The unpatched raw-34 failure reproduces, then all `0…255` complete without fataling after the
   experimental change.
3. Every boundary maps to the specified class; TWQ traces prove the corresponding lane/bucket.
4. Immediate and delayed/leeway cases pass; no delayed case is waived around missing
   `dispatch_activate`.
5. TWQ and forced-pool results are separate, engine-attributed verdicts.
6. Observation does not itself escalate the task, and raw evidence is retained.
7. One native libdispatch is loaded; `__APPLE__` is not spoofed.

### Full track — scheduling/QoS green

In addition to P1, current-thread QoS, setter/override semantics, external-thread behavior, and the
chosen ULE effect are implemented and tested under contention. Donation/inversion behavior and the
maintenance mapping have explicit verdicts. Task stealing/cooperative scheduling, if adopted, has
its own gate and is not inferred from priority canonicalization.

## BOUNDARIES / DEFAULT DISPOSITION

- **Post-preview and non-gating.** This is milestone-9 platform maturity, not a li-1000 ship gate.
