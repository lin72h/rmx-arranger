## PREAMBLE — what this project is
rmxOS is an **open-source operating system** — a Darwin/Mach userland ported onto stock FreeBSD 15, developed in the open like FreeBSD or illumos. This is a **maintainer's own code-quality check of ONE feature of our service manager (launchd)** — how, just before it runs a job, launchd sets up the child process so it starts with exactly the runtime attributes the job's config declared (its working directory, resource limits, run-as user/group, umask, standard-input/output files, and environment). Ordinary pre-release engineering on our own source — the goal is simply to confirm this one path is well-built for our own users.

## THE ONE FEATURE (this is the whole scope)
launchd's **pre-exec child setup** — `job_setup_attributes` (`core.c:5214`, declared `:817`, called from the child at `:4637`) and its file helper `job_setup_fd` (`core.c:5314`). Between fork and exec, in the child, launchd applies, in order: process priority/nice (`:5219`), the per-job resource limits (`setrlimit` loop `:5223-5240`), session creation (`:5242`), i/o policy (`:5246-5251`), root/working directory (`chroot`+`chdir` `:5252-5255`, `workingdir` `:5259-5267`), the run-as user/group (`job_postfork_become_user` `:5257`), umask (`:5269-5271`), the three standard-io descriptors (`:5273-5279` via `job_setup_fd`), the environment (`jobmgr_setup_env_from_other_jobs` + per-job `setenv` loop `:5281-5285`), and the process-group / session decision (`setpgid` vs `setsid` `:5307-5311`). Confirm this one setup path leaves the child with exactly the declared attributes before exec — nothing wider.

## CONTEXT
This is the last thing launchd does before a job becomes itself: lay down the environment the job's author asked for. A quiet bug here means a job runs with the wrong current directory, an unapplied limit, the wrong descriptor on stdout, or a missing environment variable — and because the job still *starts*, that kind of setup slip rarely shows up in a flat "did it launch" check. It complements op-264 (keep the running job supervised) and op-273 (fire the job at the scheduled time): this is how the job is *dressed* for its run. Plain software-engineering framing: attribute-application order, descriptor wiring, environment assembly, and per-step failure handling.

## THE QUESTIONS (all about this one path)
1. **Attribute application + ordering.** Are the declared attributes — nice, the `setrlimit` soft/hard pairs, i/o policy, root/working directory, umask, and the run-as user/group — each applied correctly and in a coherent order (e.g. directory and user changes sequenced so neither undoes the other), with each `job_assumes_zero_p`-guarded step's failure logged rather than silently skipped? Does a job that declares none of these get a clean default child?
2. **Standard-io descriptor wiring.** Does `job_setup_fd` (`:5314`) open each declared path with the documented flags (stdin `O_RDONLY|O_CREAT`, stdout/stderr `O_WRONLY|O_CREAT|O_APPEND`), `dup2` it onto the right target descriptor (0/1/2), and close the source descriptor so nothing extra is left open — and is the `stdin_fd` inherited-descriptor branch (`:5273-5277`) handled consistently with the path branch?
3. **Environment assembly.** Does the environment the child ends up with match what the config declares — the manager-supplied variables (`jobmgr_setup_env_from_other_jobs` `:5281`) plus the per-job `env` entries (`:5283-5285`) — with the documented precedence when both name the same key, and nothing dropped or doubled?
4. **Session / process-group + partial-setup behavior.** Is the `setpgid`-vs-`setsid` choice (`:5307-5311`) correct for both the top-level and the re-parented case, and if an early step in the sequence fails, does the child continue into exec in a well-defined state (the documented best-effort) rather than proceeding with a half-applied, inconsistent setup?
