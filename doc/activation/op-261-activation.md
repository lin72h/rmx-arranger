## THE ONE FEATURE (this is the whole scope)
The `mach_msg` receive path's handling of an **oversized received message** — one larger than the caller's buffer — and how **libdispatch** (the one consumer that exercises this path) reads the result. In a first review we landed a fix (**op-249, commit `59fe7b30`**) so an oversized receive returns its status cleanly and keeps the message on the queue, instead of reaching the error-return helper with a caller-local buffer handle that was never initialized. Confirm this one path is complete and clean **after** the fix — nothing wider.

## CONTEXT
When a caller posts a receive with a buffer too small for the next message, the routine must report that cleanly and leave the message on the queue — without touching a caller-local buffer handle that was never set. Our fix touched three lines across two files: `mach_msg.c:326` initializes the handle to a null sentinel; `mach_msg.c:380` guards the error-return helper on the handle being non-null; `ipc_mqueue.c:774-792` routes an oversized-receive result through the "done" path that keeps the message on the queue. This pass re-reads those three edits **together** for mutual consistency, plus the one consumer (libdispatch's message-servicing loop) that reads the new return behavior. Plain software-engineering: return-path consistency, an init/guard invariant, and consumer agreement after our own change.

## THE QUESTIONS (all about this one path)
1. **Return-path consistency.** Are the three edits mutually consistent — is there ANY other return path out of the receive routine that reaches the error-return helper (`mach_msg.c:380`) with the buffer handle still at its null sentinel, or any path that skips the init at `mach_msg.c:326`? Does the oversized-receive case route through the "keep-on-queue / done" path (`ipc_mqueue.c:774-792`) and return its status cleanly on **every** branch?
2. **Init/guard invariant.** The handle is set to a null sentinel at `:326` and the error helper is gated on non-null at `:380`. Is that invariant actually maintained across the whole routine — the handle definitely non-null on every path that legitimately reaches the helper, and definitely at its sentinel on every path that must skip it? Any early branch that reads or sets the handle out of order?
3. **libdispatch consumer agreement.** libdispatch is the code that exercised the oversized-receive path. Now that op-249 changed how an oversized receive is returned, does libdispatch's message-servicing loop still agree with the new return behavior (it reads the status and re-arms) — or does any branch still assume the pre-fix behavior?
4. **Trailer-boundary case.** The 1st review's acceptance run exercised the plain oversized case, but a trailer-sized boundary case was not runtime-exercised (a test-harness bug, not the code). By inspection, given the fix, does that boundary case return correctly on this path — or is it worth a dedicated **needs-runtime-check**?
