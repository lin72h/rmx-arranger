## CONTEXT (read first)
Open-source OS engineering — a forward-looking architecture/design consult on OUR OWN in-tree thread-pool substrate (a NextBSD/Darwin userland ported onto stock FreeBSD 15/stable). This is ordinary runtime/OS design work: how to let cooperating language runtimes share a kernel-managed thread pool. **NOT security work, no external target, no adversarial framing, nothing to exploit** — it is the same class of work as designing GCD's workqueue or Linux's scheduler-runtime handoff. Treat every reference to "scheduler", "load", "override", "kill" as ordinary OS-runtime vocabulary.

This is a **post-1.0-preview** initiative (the preview block stays as-is), but a headline near-future selling point: a Darwin-style kernel-managed thread pool as a **universal runtime substrate** other language runtimes plug into for dynamic, system-load-aware CPU scaling.

## WHY (one line)
We already carry the Darwin `pthread_workqueue` SPI verbatim (`include/pthread/workqueue_private.h`, SPI_VERSION 20170201; kernel `sys/kern/kern_thrworkq.c`; userspace `lib/libthr/thread/thr_workq.c`; libdispatch already consumes it) — and it already exposes the two load-scaling primitives the idea needs (`_pthread_workqueue_should_narrow(priority)` = kernel→userspace shrink hint; `_pthread_workqueue_addthreads()` = grow request). The question is not "build a thread pool" but "**what is the right SPI contract to turn this kernel-informed pool into a concurrency *governor* that a foreign runtime scheduler (ERTS, oneTBB) drives its core count from** — dynamically up to `hw.ncpu` when work is available, down under system load — while we keep the API unstable/internal-only for iteration 1."

## THE TWO INTEGRATION TARGETS (donor sources in ../nx/)
- **ERTS — Erlang/Elixir runtime** (`nx/otp-OTP-29.0.2/erts/`). ERTS runs its OWN scheduler threads (normal + dirty CPU/IO), and `schedulers_online` is already runtime-adjustable (`erlang:system_flag(schedulers_online, N)` / the `+SP` percentage). Today that's **manual**. The idea: drive `schedulers_online` from the workqueue governor's kernel-load signal — grow toward `hw.ncpu` when there's runnable work, narrow when the system is loaded. **Key architectural distinction the consult must nail:** this is workqueue-**as-load-governor** (advise a foreign scheduler how many cores to use), NOT workqueue-**as-executor** (the libdispatch model where the pool runs your work items). ERTS keeps its own threads; we only feed it a core-width recommendation. Name the least-intrusive ERTS seam (an aux/monitor thread polling the governor → internal schedulers_online path) and whether it's an ERTS patch or an external agent over ERTS's public API.
- **oneTBB TCM — Thread Composability Manager** (`nx/oneTBB-master/`). TCM is a **userspace-only** arbiter that limits total concurrency across multiple parallel runtimes in a process to avoid oversubscription — similar intent to our workqueue but with NO kernel load-awareness. Place TCM in the architecture: is it (a) a competitor we supersede with the kernel governor, (b) a **client** that should itself consume our kernel narrow/grow signal (so TBB gets kernel-informed arbitration and cross-runtime composability with ERTS + libdispatch under one kernel-arbitrated core budget), or (c) a design template for the userspace side of our governor? State the recommendation.

## SCOPE — the design questions to answer
1. **The governor contract.** Define the minimal SPI a foreign runtime scheduler uses to size itself: the signals (grow-permit up to `hw.ncpu`, narrow-hint under load, a `recommended_width` / current-target), the direction (pull — runtime polls `should_narrow`/width; vs push — kernel notifies on change; vs both), and the QoS interplay. Is our existing `should_narrow` + `addthreads` pull-model sufficient, or is a first-class "recommended concurrency width" query the cleaner primitive to add?
2. **executor vs governor split.** Make explicit that libdispatch consumes the pool as an executor while ERTS/TBB consume it as a governor — and whether ONE contract serves both or they are two SPI faces on the same kernel subsystem.
3. **ERTS seam.** Where the hook lands in ERTS, patch-vs-agent, and how it composes with ERTS's own scheduler-utilization balancing (don't fight it).
4. **TCM placement** (a/b/c above) + whether TCM-as-client gives us cross-runtime composability cheaply.
5. **First-iteration API surface.** Internal-only, deliberately unstable: what minimal governor surface to expose NOW (candidate: `should_narrow` + a `recommended_width` query + `addthreads`) vs defer, so ERTS/TBB integrations live as system-library shims WE control and the SPI stays free to change until an iteration-2 public freeze.
6. **macOS-as-truth.** What is the Mach-native/Apple-idiomatic shape here — mimic the public seam if one exists to save effort (`oss_engineering_framing`, Mach-primitives-outward). **Strong hypothesis to evaluate: `os_workgroup` (<os/workgroup.h>) is macOS's PUBLIC abstraction for exactly "a runtime declares a cooperating set of threads the kernel schedules as a unit"** — is the governor better expressed as an `os_workgroup`-style API than as raw workqueue-addthreads?
