## PREAMBLE — what this project is
rmxOS is an **open-source operating system** — a Darwin/Mach userland ported onto stock FreeBSD 15, developed in the open like FreeBSD or illumos. This is a **maintainer's own code-quality check of ONE feature of our notification service** — how the notifyd daemon tracks client name registrations, delivers posts, and cleans up on cancel. Ordinary pre-release code-quality engineering on our own source. No target, no adversary, nothing to exploit — the goal is to confirm this one path is well-built for our own users.

## THE ONE FEATURE (this is the whole scope)
The notifyd **name-table lifecycle** — how the daemon adds a client registration for a name, coalesces multiple registrations on the same name, delivers a post to registered clients, and removes the entry on cancel or client death. Client side: `lib/libnotify/libnotify.c` / `notify_client.c` (register/post/check/cancel). Daemon side: `usr.sbin/notifyd/notifyd.c` / `notify_proc.c` (the name-table + delivery). Confirm this one path keeps its bookkeeping balanced — nothing wider.

## CONTEXT
A notification service's core job is: register interest in a name, get told when it fires, and clean up when done. The leg-4 soak proved this stays balanced at runtime (register==cancel per sample, flat port-slope over 2h), but the name-table code itself was never read for correctness — this focused pass does that before higher-level features lean on it. Plain software-engineering framing: table-entry lifetime, register/cancel balance, coalescing correctness, cleanup on client death.

## THE QUESTIONS (all about this one path)
1. **Register / cancel balance.** Every register that adds a name-table entry (and any Mach port or fd it holds for delivery) is matched by a cancel/cleanup that removes it and releases what it held — on the normal path and when the client goes away without cancelling. Any path that adds an entry but can miss the removal?
2. **Coalescing.** When multiple clients register the same name (or one client registers repeatedly), is the shared/coalesced state tracked with a correct count — so the Nth cancel removes exactly its own registration and the entry is freed only when the last one goes, never early (dropping a live client) and never late (leaking the entry)?
3. **Post delivery.** A post walks the registered clients for a name and signals each. Is that walk safe against the list changing (a client cancelling or dying mid-delivery), and does a delivery failure to one dead client not abort delivery to the rest or leak the failed client's slot?
4. **Client-death cleanup.** When a registered client dies, does the daemon reliably reclaim all its name-table entries and delivery resources (this is the property the soak's flat port-slope depends on) — or is there a registration shape whose cleanup only runs on explicit cancel?
