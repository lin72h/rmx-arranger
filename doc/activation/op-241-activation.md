## OUTCOME (Arranger-verified first-hand at explorer 4c96652 + canonical ipc_kmsg.c, 2026-07-02)
**PREMISE CONFIRMED, ACCEPTED at 9/10 — the "dark" label is NOT stale.** A single-message MACH_RECV dispatch-source round-trip on the alpha triggers a kernel panic: `panic: mtx_lock() of spin mutex (null)` in `ipc_kmsg_copyout_dest → msg_receive_error → mach_msg_receive`. First-hand empirical panic (not code-reasoned) → I accept the premise verdict. The panic site is real code: `ipc_kmsg_copyout_dest` does `io_lock(dest)` (canonical `ipc_kmsg.c:2853`; the report's `:2844` is explorer-tree line drift — same function). **Reconciles with op-098** (id-003 DROP): op-098 traced the SUCCESS path (`filt_machport×3 → mach_msg_receive`, raw round-trip, no panic); op-241 hits the ERROR path (`msg_receive_error`) via the dispatch source. Different paths — NO contradiction, no regression of op-098.

**ROOT-CAUSE REFINED — the report's proposed fix is REFUTED by its own evidence (the op-240 pattern):**
- Report claims: "FIX: ensure port creation/insert_right initializes `io_lock_data`." **Contradicted first-hand:** the probe's `mach_msg(MACH_SEND_MSG)` on `recv_port` SUCCEEDED (the kevent fired, which only happens after the message lands). The **send path also takes `io_lock(dest)` on that same port** — if its lock were NULL, the SEND would have panicked before the receive. It didn't. So the lock was non-NULL at send; a NULL lock at receive-error copyout has a DIFFERENT cause (stale/freed `dest` pointer, use-after-free, or a malformed kmsg header on the error path).
- **Two open questions the report skipped, both must be answered by trace BEFORE any fix:** (1) WHY does `mach_msg_receive` take the `msg_receive_error` path at all (op-098's receive succeeded)? (2) WHAT is `dest` at the `io_lock` panic — a real port with a nulled lock (init/UAF), or a non-port pointer that passed `IO_VALID`?
- **Probe-design suspicion (severity input):** the probe arms the dispatch MACH_RECV source AND has the handler do its own `mach_msg(MACH_RCV_MSG)` on the same `recv_port` (probe.c:70-87) — a potential double-drain. The MACH_RECV handler-receives idiom IS Apple-canonical, so this is representative; but whether the source's internal servicing races the handler's receive is exactly what the trace must settle (and bears on whether real consumers notifyd/libxpc hit it).

**Verdict: LIVE GAP (premise accepted 9/10) → kernel-level, routed to op-242 (Implementer, premise-gated).** The reproducer (`findings/nx-r64z/dtrace/mach-recv-premise/mach_recv_probe.c`) is the smallest falsifiable trigger. The FIX is NOT yet known — do not implement the report's guessed init-fix on spec.

**PREVIEW SEVERITY (flag, not a self-declared gate — `no_conflate_gating_with_readiness`):** MACH_RECV sources back **notifyd + libxpc + Swift XPC** (3 preview-critical core services). A kernel panic reachable from the idiomatic public dispatch API is a candidate **preview-blocker** — but severity/gating is a **Coordinator** call (new decision **C6**, filed to li-1013).
