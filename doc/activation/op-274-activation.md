## WHAT THIS IS
Forward-looking distribution-engineering design for **rmxOS 1.0-preview**: how the OS is laid down on disk by the installer and how it is moved from one release to the next by the updater. rmxOS is an open-source Darwin/Mach userland on stock FreeBSD 15, and it already ships on OpenZFS. The design idea is to make the on-disk layout and the update transaction take full advantage of three things that compose naturally: (1) **OpenZFS as the root filesystem**, so a release-to-release update can be shipped and applied as a cheap **`zfs send`/`zfs receive` incremental** between two snapshots rather than a file-by-file copy; (2) a **Fedora-Atomic-Desktop-style immutable base** — the OS ships as a whole, swapped as a unit, with a clean split between the shipped base and the machine's own state; and (3) the **macOS sealed-system layout** where `/bin`, `/sbin`, and `/usr/*` are a read-only base the user does not modify in place. Because rmxOS controls its whole base, it can afford this immutability. The goal is an installer + updater that grow directly out of these three, with an **atomic apply and a clean rollback** to the prior boot environment. Ordinary OS-distribution design on our own tree — no target, no adversary.

## SCOPE — the design questions to answer
1. **Root dataset layout + boot environments.** Propose the ZFS dataset hierarchy that separates a **read-only shipped base** (the datasets backing `/`, `/bin`, `/sbin`, `/usr/*`) from **machine-owned mutable state** (`/etc` overrides, `/var`, `/home`, and any app/user data), such that a whole OS release is one **boot environment** (a clonable dataset root) the loader can select at boot. Which directories are base vs. state, where the split lines fall (notably `/etc` and `/var`), and how a new boot environment is cloned and activated without disturbing the running one.
2. **The incremental update transaction (`zfs send`/`receive`).** Design the release-to-release update as an incremental between the installed base snapshot and the new release snapshot: how the update artifact is produced (`zfs send -i old new`), how it is received into a new boot environment, and how the whole thing **applies atomically** (the new environment becomes default only once fully received and verified) with a **rollback** that reactivates the prior environment if the new one fails to boot or is rejected. Cover the case where the machine's installed base is more than one release behind (incremental chain vs. a full send fallback), and how the base snapshot is reconciled if local state has diverged.
3. **Enforcing the immutable/sealed base + separating mutable state.** How the read-only base is actually held read-only at runtime (dataset `readonly=on`, mount-time flags, or an overlay), and how the small set of legitimately-writable paths that live *inside* nominally-base trees (e.g. `/etc` machine config) are handled — an overlay/redirect for `/etc`, symlink-to-state, or an explicit writable dataset carved out. Nail how a user or package that expects to write under `/usr` is handled given the base is read-only, and where third-party/add-on software lands so it survives a base swap.
4. **The installer's first-provisioning path.** Design the initial install: pool/dataset creation, laying down the first base boot environment from the preview image (composing with the id-015 staging model, not replacing it), seeding the mutable-state datasets with defaults, and installing the loader's boot-environment selection so the very first boot and the first update use the *same* mechanism. Keep it minimal and preview-grade.
5. **Composition + first-iteration surface.** State how this composes with the retired id-015 staging model (what the installer reuses vs. adds) and with the deferred id-012 pipeline (what is deliberately left out now). Define the **minimal iteration-1 surface** to build for 1.0-preview — candidate: single-track boot environments + incremental receive + one-step rollback — and what to defer (multi-track/staged rollouts, delta compaction, GC of old environments) so the mechanism stays changeable.
