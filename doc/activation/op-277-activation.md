## WHAT THIS IS
Forward-looking architecture design for **openclaw**, the first real userspace application we are bringing onto rmxOS. rmxOS is an open-source Darwin/Mach userland on stock FreeBSD 15; openclaw (`~/wip-openclaw/nx/openclaw`, MIT) is a large Node/TypeScript **monolith** described as a "Multi-channel AI gateway with extensible messaging integrations." We want it to run well on our platform AND to take advantage of what our platform uniquely offers (Darwin launchd lifecycle, our libxpc IPC, and our kernel-managed GCD/`pthread_workqueue` dynamic concurrency). The question is a pure design one: **what is the best integration + optimization strategy** — evaluate the three strategies below, find the concrete optimization points in openclaw's real architecture, and add further strategy categories if warranted. Ordinary open-source application-porting design on code we control — no target, no adversary.

## GROUND ALREADY SET (Arranger first-hand read of `~/wip-openclaw/nx/openclaw`, 2026-07-07 — state as given, confirm at source)
- openclaw is a pnpm-workspace monolith: `name: openclaw`, `version: 2026.4.6`, `bin: openclaw → openclaw.mjs`, `main: dist/index.js`, `type: module`.
- Extensible surface: a published **plugin-sdk** (`./plugin-sdk`, `/core`, `/provider-setup`, `/sandbox`, `/self-hosted-provider-setup`) — providers/plugins are the natural modularity seam.
- Native app shells: `apps/{macos,ios,android,shared}`. macOS integration is already present, including a **Sparkle `appcast.xml`** auto-updater.
- Channel/feature packages: `packages/{clawdbot,moltbot,memory-host-sdk,plugin-package-contract,plugin-sdk}` + `extensions/*`; messaging integrations (discord/matrix/baileys/…).
- Heavyweight native deps that shape any port/split: `node-pty`, `node-llama-cpp`, `sharp`, `@napi-rs/canvas`, `@matrix-org/matrix-sdk-crypto-nodejs`, `koffi`, `protobufjs`.
- Port is in early integration in `~/wip-openclaw/wip-codex54x` (FreeBSD porting notes + patch queue).

## THE THREE STRATEGIES (Coordinator-set precedence — evaluate each, then extend)
- **strategy-A — light up openclaw's macOS-native paths on rmxOS where they make sense.** Because rmxOS is a Darwin userland, the Darwin/macOS integration openclaw already carries can run natively instead of falling back to a generic-Unix stub. Candidate points: launchd/LaunchAgent lifecycle for the long-running gateway, the Sparkle updater mapping onto our platform updater, and any `apps/macos` / Darwin-API usage that is currently conditional. Which of these are worth enabling for 1.0, and which are cosmetic?
- **strategy-B — break the monolith into small, on-demand processes.** Split the single Node process along its natural seams (channels, providers, plugins, the memory host) into small processes that **launchd loads and unloads on demand**, so idle capacity costs no memory and the footprint tracks real use. Which seams split cleanly, what the per-process granularity should be (one-per-channel? one-per-plugin? a shared broker + leaf workers?), how they talk (our **libxpc** IPC), and what the memory/latency/cold-start trade is.
- **strategy-C — (built on B) rewrite the hot small processes in Swift** so they ride our **GCD / `pthread_workqueue` dynamic concurrency** (kernel-managed thread width, no thread explosion) and other rmxOS-unique runtime features. Which of the split processes are worth moving off Node to Swift (the compute/IO-hot ones vs. the ones that must stay Node for a native-dep or SDK reason), where the Node↔Swift boundary lands, and how the Swift workers size themselves from the concurrency governor so many small processes share ONE load-aware core budget.

## SCOPE — the design questions to answer
1. **Port-surface characterization.** From the real tree, characterize openclaw's runtime shape as it bears on integration: the single-process/event-loop model, the plugin-sdk process/execution model, the native-dep set (which deps are portability pain on FreeBSD/rmxOS, which have Swift or in-tree equivalents), and the current macOS-conditional code paths. This is the ground the A/B/C calls rest on.
2. **Strategy-A optimization points.** Enumerate the macOS-native paths worth enabling on rmxOS and the concrete win of each: launchd lifecycle for the gateway, the updater mapping onto our ZFS/immutable platform updater (op-274), and any Darwin-API path that currently stubs to generic-Unix. Rank by win/effort; flag any that are a trap (an API we do not implement).
3. **Strategy-B split design.** Recommend the seam(s) to split the monolith along, the process granularity, the launchd **on-demand load/unload** wiring (the op-268 demand-launch path + op-275 pre-exec setup), the **libxpc** message boundary between processes, and the state/session that must be shared vs. can be per-process. Call the memory/cold-start trade-off explicitly and what stays a single long-running core vs. what becomes on-demand leaves.
4. **Strategy-C Swift-rewrite design.** Recommend which split processes are worth rewriting in Swift, the Node↔Swift boundary, how the Swift workers consume our GCD/`pthread_workqueue` governor (op-265) to size concurrency without thread explosion, and which processes should stay Node (native-dep-bound, SDK-bound, or not hot enough to earn a rewrite). State the sequencing: C is built on B, so what B has to settle first.
5. **Extend the strategy set + sequence the roadmap.** If the architecture warrants strategy categories beyond A/B/C, add them (candidates the Oracle should consider: a shared state/cache plane across the split processes; a native-dep substitution plane; a build/packaging plane for shipping the split app under our updater). Then sequence the whole thing: what lands for **1.0-preview** vs. later, honoring the A→B→C precedence, each item bucketed by effort/risk.
