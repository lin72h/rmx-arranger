## WHAT THIS IS
Forward-looking API/architecture design on OUR OWN in-tree thread-pool code — the same class of work as designing any language runtime's thread-pool interface. rmxOS carries a kernel-managed thread pool (`pthread_workqueue`) that already produces two load-scaling signals: a **narrow hint** (the kernel tells userspace to shrink its worker count when the system is loaded) and an **add-threads grow request** (userspace asks to grow, up to the hardware core count, when there's runnable work). The question is a pure design one: **what is the right API for a foreign runtime scheduler (Erlang's ERTS, Intel's oneTBB) to size its own thread/core count from that load signal** — grow toward the hardware core count when work is available, narrow under system load — so cooperating runtimes share one load-aware core budget instead of oversubscribing the machine. No target, no adversary — ordinary concurrency-runtime design.

## THE TWO INTEGRATION TARGETS (open-source donor runtimes in ../nx/)
- **ERTS — the Erlang/Elixir runtime** (`nx/otp-OTP-29.0.2/erts/`). ERTS runs its OWN scheduler threads (normal + dirty CPU/IO), and its active count `schedulers_online` is already adjustable at runtime (`erlang:system_flag(schedulers_online, N)`, or the `+SP` percentage). Today that adjustment is **manual**. The design idea: drive `schedulers_online` from our pool's load signal — grow toward the core count when there's runnable work, narrow when the system is loaded. The key design distinction to nail: this is the pool **as a load governor** (advise a foreign scheduler how many cores to use; the runtime keeps its own threads), NOT the pool **as an executor** (the pool runs your work items). ERTS keeps its own threads; we only feed it a core-width recommendation.
- **oneTBB TCM — Thread Composability Manager** (`nx/oneTBB-master/`). TCM is a **userspace-only** arbiter that limits total concurrency across multiple parallel runtimes in one process to avoid oversubscription — similar intent to our pool, but with NO system-load awareness. Its placement in the design is one of the questions below.

## SCOPE — the API-design questions to answer
1. **The governor contract (the core API).** Define the minimal API a foreign runtime scheduler uses to size itself: the signals — a grow-permit (headroom up to the hardware core count when work is available), a narrow-hint (shrink under load), and/or a first-class **"recommended concurrency width"** query the runtime polls; the direction — pull (the runtime polls current width / should-narrow) vs push (the pool notifies on change) vs both. Is our existing narrow-hint + grow-request pull-model sufficient, or is a single **"recommended width" query** the cleaner primitive to add? **Design lesson to fold in (from op-252, stated as design prior-art, not a platform claim):** a clean, proven shape for this seam is a small **"parallel workgroup" abstraction** — create / join / leave a cooperating thread set, plus a **hardware-aware "recommended parallel width" query** the runtime polls to size itself, with the width signal bidirectional (a pull query complemented by a push narrow-hint). Evaluate expressing the governor as that workgroup-style API vs as the raw grow/narrow calls.
2. **Governor vs executor split.** Make explicit that a thread pool can be consumed two ways — as an **executor** (the pool owns the threads and runs your work items, like a dispatch queue) or as a **governor** (the pool owns no work; it only advises how many cores to run, and the runtime keeps its own threads). ERTS and TBB want governor. Does ONE API serve both consumption modes, or are they two distinct API faces on the same pool?
3. **ERTS seam.** Where the hook lands in ERTS, and whether it's a patch to ERTS or an external agent over ERTS's public API. Name the least-intrusive seam (candidate: a small auxiliary/monitor thread that polls the governor's recommended width and drives `schedulers_online`), and how it composes with ERTS's own scheduler-utilization balancing so the two don't fight each other.
4. **oneTBB TCM placement.** Place TCM in the design: is it (a) a competitor we supersede with the load-aware governor, (b) a **client** that should itself consume our narrow/grow signal (so TBB, ERTS, and others share one load-aware core budget and get cross-runtime composability), or (c) a design template for the userspace side of our own governor? State the recommendation, and whether TCM-as-client buys cross-runtime composability cheaply.
5. **First-iteration API surface.** Deliberately internal/unstable for iteration 1: what minimal governor surface to expose NOW (candidate: narrow-hint + a recommended-width query + grow-request) vs defer — so the ERTS/TBB integrations live as shims WE control and the API stays free to change until a later iteration-2 stabilization. Do NOT design a frozen third-party-facing API.
