## PREAMBLE — what this project is
rmxOS is an **open-source operating system** — a Darwin/Mach userland ported onto stock FreeBSD 15, developed in the open like FreeBSD or illumos. This is a **maintainer's own implementation-quality code review of two userland services we ported and ship** — the notification service (libnotify client + notifyd daemon) and the system logger (libasl client + asld daemon + aslmanager retention tool). Ordinary pre-release code-quality engineering on our own source, the kind any OS project runs before a release. There is no target, no adversary, nothing to exploit — the goal is to raise the quality, correctness, and maintainability of code we wrote for our own users. All API vocabulary is ordinary operating-system naming.

## MANDATE — IS THE IMPLEMENTATION WELL-BUILT?
notifyd and asld are foundation services the 1.0-preview and higher-level features build on. Both pass conformance (behavior matches macOS) and most durability legs — this consult answers the next question up: **is the implementation itself well-built — correct, robust, cleanly structured, resource-tight — enough that we can confidently build on it?** Be COMPLETE, not minimal: a proactive quality pass over both services' client + daemon + store code, each surface characterized **solid / uncertain / needs-runtime-check** with the evidence. Where the code is well-built, say so and why; where it's rough or unclear, characterize it and hand back a scoped follow-up.

## CONTEXT — engineering framing
A routine implementation-quality code review of our OWN ported services, by their maintainers ahead of a release. Both ride the libdispatch + compat-Mach IPC substrate and share a client→transport→daemon→(store) shape. Plain software-engineering framing throughout: API-contract correctness, object lifetime/ownership, resource (memory/fd/port) accounting, error-path handling, concurrency correctness, state-machine integrity, and code structure/maintainability — the standard quality concerns of a message-passing service plus an on-disk store.

## SCOPE — the implementation-quality questions to answer
1. **API-contract correctness.** Does the implementation correctly honor the documented client surface — notify (post / register{check,signal,mach_port,file_descriptor,dispatch} / check / cancel, coalescing, state + int64) and asl (asl_new/set/log/send, level filtering, asl_search/query, store read-back)? Return values, error codes, and edge inputs (empty/oversized/NULL, unknown name/token) handled per contract?
2. **Object lifetime & resource accounting.** Memory, fd, and Mach-port ownership across client and daemon — allocations paired with frees, ports/fds released on every path incl. error paths; no leak or double-free under registration/submit churn. (notify sampled port-slope flat; asl store-side fd/memory is exactly leg-4's open question — reason it at source.)
3. **Error-path handling.** Every failure return — transport unavailable, bootstrap unresolved, store full/unwritable, allocation failure, malformed message — leaves the client/daemon in a consistent state with correct cleanup, no partially-applied registration, no orphaned port/fd, no lock left held.
4. **Concurrency correctness.** The daemon serving multiple clients concurrently; libdispatch source arm/drain/re-arm on the notify/log Mach ports; store write vs concurrent query in asld; and asld vs aslmanager coordination on the same store (can a reclaim race a live write?). Where correctness relies on assertions, note if they compile out in production.
5. **State-machine integrity.** notifyd name-table consistency across restart/reload (state rebuild correct?); asl store rotation/retention state (asl_store/asl_file open/rotate/close) — is the on-disk state machine sound and crash-consistent by inspection?
6. **Substrate consumption.** Correct use of the libdispatch + compat-Mach IPC foundation — source lifecycle, dead-name/SEND_DEAD handling, agreement with the kernel buffer/trailer contract. Flag any consumer-side assumption a recently-hardened substrate could break.
7. **macOS-fidelity.** Where the implementation is faithful to Darwin behavior and where it diverges (coalescing under burst, store propagation latency, filter semantics, multi-client fan-out) — anything the single-shot conformance matrix did not exercise.
8. **Code structure & maintainability.** Dead code, rebase scaffolding (e.g. notifyd `n2_markers.*` NextBSD-added artifacts), portability shims, duplicated logic, or unclear ownership that should be cleaned before higher-level features depend on this code. Cheap-and-worth-it cleanups vs leave-as-is.
