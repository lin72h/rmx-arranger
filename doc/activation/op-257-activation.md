## CONTEXT (read first — engineering framing)
Ordinary open-source OS engineering: wiring a log-retention helper (`aslmanager`, the ASL store rotation/reclaim tool) into an rmxOS soak-test image's launchd so the on-disk log store gets pruned, exactly as macOS ships it. rmxOS = Darwin/Mach userland on FreeBSD 15; `usr.sbin/aslmanager/` is already in-tree. This is service-wiring + image-build work on our own daemon, not security work — no target, no adversary.

## WHY (one line)
op-163 (asl leg-4 soak) FLAGGED its "store growth bounded + aslmanager reclaims" bar: the on-disk store was never pruned because **no aslmanager launchd job is present in the soak image** (op-170 audit, verdict `aslmanager-not-wired`, Arranger-verified first-hand @ commit 263c21c). Wiring it — and forcing at least one reclaim inside a soak window — is the last product-side step before asl leg-4 can be re-soaked to truly-green.

## BASELINE (op-170 findings — take as given; read the note to source-confirm before editing)
- Findings: `rmx-explorer` `findings/nx-r64z/20260627-op170-aslmanager-wiring-audit.md` (commit 263c21c). Read `OP170_ASLMANAGER_WIRED` (absent + intended load path), `OP170_RECLAIM_TRIGGER` (aslmanager.c trigger condition + default threshold, file:line), `OP170_WOULD_HAVE_FIRED`, `OP170_STORE_RETENTION`.
- Key op-170 mechanism to respect: the op-163 RSS growth (6→45MB) was **I/O buffering, not a retention leak** — `asl_store.c` file_cache is fixed-size, on-disk FILE*-backed. So the leg-4 quantity that actually matters is the **on-disk store size + a real reclaim**, NOT RSS. Do not "fix" RSS growth; wire retention.
- Soak image lineage: op-163 soaked `build/op162-leg2/op162-leg2.img` (Apple asld on `com.apple.system.logger`, provenance held). Build the new soak image from the current canonical alpha, carrying the asld overlay this image already proved.
- **op-260 corroboration (Arranger-verified first-hand 2026-07-03):** the in-daemon `trigger_aslmanager()` is a dead no-op — its whole body is `#if 0`'d (`usr.sbin/asl/daemon.c:853-881`, confirmed at source), and `asl_store.c:690` carries the matching XXX. So asld NEVER self-triggers a reclaim; the ONLY reclaim path is an external aslmanager run. This CONFIRMS op-257's approach (a launchd job with a forced `StartInterval`, SCOPE-1/2) is the right one — do NOT try to un-stub the in-daemon trigger for the soak; drive reclaim externally. (Un-stubbing `trigger_aslmanager` is a separate product question, not this op.)

## SCOPE
1. **Add the aslmanager launchd job to the soak image.** Stage `com.apple.aslmanager.plist` (or the macOS-faithful equivalent name aslmanager expects) so launchd owns the reclaim helper. Match the macOS plist shape on the load-bearing keys (`launchd_plist = macOS fidelity` — faithful on what matters, catalog exotic keys). Note per `launchd no auto-scan`: a staged plist is INERT until `launchctl load`+start runs it — so also wire the load into the image's rc.local/launchd-bringup path the same way the asld job is brought up, or the job never runs.
2. **Force a reclaim to be observable inside a soak window.** aslmanager's stock trigger (per op-170 `OP170_RECLAIM_TRIGGER`) is likely a size/TTL/schedule that would NOT fire in a few-hour soak. For the SOAK-TEST image only, set an aggressive-but-honest trigger — a short `StartInterval` and/or a lowered store-size / TTL threshold — so a normal soak crosses it and aslmanager runs ≥1 real reclaim cycle. Document the delta from the stock default (this is a test-image config, not a product default change).
3. **Emit a reclaim marker the soak oracle can key on.** The op-133 oracle watches for aslmanager-reclaim; confirm the reclaim path produces an observable signal (fbt on the aslmanager reclaim entry, or a store-file-count/size drop) so op-258 can assert PLATEAU-across-reclaim. 4. **Build + stage the image; report its identity.** Rebuild the soak image with (1)-(3); report the image path + a content check (mount/readelf/hash) proving the aslmanager job + asld overlay are both present (`artifact identity needs content check` — do not claim lineage from size/filename).
