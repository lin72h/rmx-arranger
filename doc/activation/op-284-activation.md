## CONTEXT (engineering framing)
Ordinary open-source OS engineering on our own IPC library. rmxOS = Darwin/Mach userland on FreeBSD 15. libxpc is one of the four 1.0-preview core services. This measures whether a source-confirmed object-layout defect actually manifests at runtime, BEFORE we edit the lifecycle code. No target, no adversary.

## WHY (one line)
The 1.0-preview solidity consult (oracle2, Arranger-verified first-hand at source) found that `struct xpc_connection` carries NO generic object header, yet `xpc_get_type`, `xpc_retain`/`xpc_release`, and `xpc_object_destroy` all cast a connection to `struct xpc_object` and read type/flags/refcount from bytes that actually overlay the `xc_name` pointer — a solid defect whose real exposure needs a runtime read before we commit a lifecycle fix.

## THE CONFIRMED SOURCE DEFECT (Arranger-verified 2026-07-10, so the probe is measuring a real thing)
- `struct xpc_object` begins `xo_xpc_type`(u8)/`xo_flags`(u16)/`xo_refcnt`(u32) (`lib/libxpc/xpc_internal.h:85-93`); `struct xpc_connection` begins `xc_name`(ptr)/ports/... with NO generic header (`xpc_internal.h:109-136`).
- `xpc_connection_create` (`xpc_connection.c:50-104`) mallocs+zeroes the connection struct and sets no type/refcount.
- `xpc_get_type` (`xpc_type.c:467-474`) returns `xpc_typemap[xo->xo_xpc_type]` — for a connection that byte is the low byte of `xc_name`: anonymous (name==NULL) → index 0 → NULL (not `XPC_TYPE_CONNECTION`); named → low byte of a heap pointer → garbage / out-of-bounds in the 18-entry map (`xpc_type.c:133-152`).
- `xpc_retain`/`xpc_release` (`xpc_misc.c:151-176`) read `xo_flags`/`xo_refcnt` which overlay the middle/high bytes of `xc_name`; `xpc_object_destroy` (`xpc_misc.c:139-149`) special-cases only dict/array then `free()` — no connection teardown of ports/queues/sources/blocks/pending/peers.
- The listener creates an anonymous peer `xpc_connection_create(NULL, NULL)` and submits it before the message (`xpc_connection.c:559-586`); aslmanager installs the peer handler only after an `XPC_TYPE_CONNECTION` comparison succeeds (`usr.sbin/aslmanager/aslmanager.c:1555-1603`), which by inspection is false for the zeroed anon peer — BUT the server path is gated on managed mode (`aslmanager.c:1585-1593`).

## WHAT TO MEASURE (premise-check, from the consult's own suggested probe)
On the candidate guest, in a small harness under a crash/leak/resource observer:
1. **Type identity.** Create an anonymous connection (`xpc_connection_create(NULL,NULL)`) and a named/mach-service connection; call `xpc_get_type` on each. Record the returned type. Expectation from source: anon → NULL, named → garbage/possible OOB. Confirm or refute at runtime.
2. **Retain/release balance.** On both connection kinds: balanced retain then release, and a resume/cancel/final-release sequence. Watch for early free (anon: fake count starts at 0 → frees on first release), never-freed leak (named: fake count = pointer high bytes), and any corruption/crash. Record owned-resource (port/queue/source) leak at teardown.
3. **aslmanager accept path — the real-consumer drive.** Bring aslmanager up in its server/managed mode and drive ONE real client request through its listener; observe whether `accept_connection()`'s `XPC_TYPE_CONNECTION` comparison succeeds and whether the peer handler is actually installed before first-message delivery. If managed mode cannot be reached in the preview config, record THAT as the exposure bound (defect present but not on any live preview path).
