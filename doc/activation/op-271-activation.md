## PREAMBLE — what this project is
rmxOS is an **open-source operating system** — a Darwin/Mach userland ported onto stock FreeBSD 15, developed in the open like FreeBSD or illumos. This is a **maintainer's own code-quality check of ONE feature of our IPC library (libxpc)** — how a structured value (a dictionary of typed values) is turned into a byte form to send to another of our processes and rebuilt faithfully on the other side. Ordinary pre-release engineering on our own source — the goal is simply to confirm this one path is well-built for our own users.

## THE ONE FEATURE (this is the whole scope)
libxpc's **value serialization roundtrip** — `xpc_pack` / `xpc_unpack` (`lib/libxpc/xpc_misc.c:109-140`) and the type conversion they delegate to, `xpc2nv` / `nv2xpc` / `xpc2nv_primitive` (`lib/libxpc/xpc_dictionary.c:37-53+`). An xpc object (dictionary / array / primitives) is converted to an nvlist and packed to bytes on send, and unpacked + converted back to an xpc object on receive. Confirm that this conversion preserves the value faithfully across the roundtrip — nothing wider. The underlying FreeBSD **nvlist** pack/unpack library (`subr_nvlist.c` / `subr_nvpair.c`) is a stock lower layer — treat it as a trusted dependency, NOT part of this scope.

## CONTEXT
Every xpc message rides this conversion: an object graph on one side must reappear as an equivalent object graph on the other. If a type maps wrong, a nesting level flattens, or an empty value vanishes, a caller silently receives a different message than was sent — the kind of quiet fidelity bug that unit conformance (which tends to exercise flat string dictionaries) can miss. This is the read-once companion to op-263's correlation work: op-263 confirmed the right message reaches the right waiter; this confirms the message's *contents* survive the trip. Plain software-engineering framing: type fidelity, nesting fidelity, empty/edge values, and conversion-failure handling.

## THE QUESTIONS (all about this one path)
1. **Type fidelity.** Does each xpc value type (bool, int64, uint64, double, string, data, uuid, dictionary, array, and the null value) convert to an nvlist entry on the way out and back to the SAME xpc type and value on the way in — a roundtrip that preserves both type and value, with no type that silently becomes a different type or is dropped?
2. **Nesting fidelity.** Are nested dictionaries and arrays rebuilt with the same shape — no nesting level flattened or lost, and container membership/order preserved per the type's documented semantics?
3. **Empty and edge values.** Do an empty dictionary, an empty array, an empty string, a zero-length data value, and a key carrying the null value each roundtrip to an equivalent object — rather than disappearing or coming back as a different kind of value?
4. **Conversion-failure handling.** If a value has no nvlist mapping (an unsupported xpc type) or a conversion helper returns nothing, is that handled with a clean, well-defined result — a definite failure return or a documented skip — rather than a partially-built object or a silently-mistyped entry?
